Message Queue and Stream data is now deleted in bounded batches instead of in one large transaction. This applies to deleting a queue or a stream and to the retention garbage collection of last-value queues and streams.

Deleting a queue or a stream through the API now returns before its data is deleted. The queue or stream is marked as being deleted, and its data is deleted in the background. While it is marked:

- Published messages are no longer written to it.
- It is still listed, with a `deleted_at` field that holds the deletion request time, so its deletion can be retried. Getting or updating it returns 400.
- A queue's consumer is stopped and does not start again.
- Stream subscribers stop receiving messages from it, as if the stream were removed.
- A new queue or stream with the same name cannot be created.

Deleting it again schedules the deletion again. This retries a deletion that failed or that returned 503 because the deletion workers were not available.
