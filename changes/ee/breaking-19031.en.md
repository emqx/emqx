`etc/ssl_dist.conf`, the Erlang distribution TLS option file EMQX ships, enables peer certificate verification by default: its `server` and `client` entries now verify the peer certificate. Peer verification can still be turned off explicitly, in a modified `etc/ssl_dist.conf` or in a custom file named by `EMQX_SSL_DIST_OPTFILE`.

This is a breaking change only for a deployment that uses the Erlang distribution over TLS, where the file is read because `cluster.proto_dist` is set to `inet_tls` or `inet6_tls`. Its `server` and `client` entries now both set `{verify, verify_peer}`, the server also requires the peer to present a certificate (`fail_if_no_peer_cert`), and the `client` entry names `client-cert.pem` and `client-key.pem` so that a node can present a certificate when the peer asks for one. The CA named in `cacertfile` is enforced on both sides.

The certificate chain is verified, but the peer's host name is still not checked against its certificate, so any certificate issued by a CA listed in `cacertfile` is accepted for any node. Give every node certificate a dNSName/iPAddress subject alternative name that matches the node's host part and remove `server_name_indication` from the `client` entry to bind the certificate to the node as well.

A cluster whose nodes all present a certificate issued by a CA listed in `cacertfile` is unaffected, because they can still verify each other. EMQX no longer ships example certificates, so a deployment that uses `inet_tls` provides the set `etc/ssl_dist.conf` names itself, and every node has to present a certificate from one CA. A cluster whose nodes do not share a CA stops connecting after the upgrade: look for `unknown_ca` or `no_client_certificate_provided` in the node logs. This includes a cluster upgraded from a release that shipped a different example CA, so align every node on one CA before the restart. Do not spread that restart over a mixed set of versions either: an older node cannot present a client certificate, so a mixed cluster keeps failing until every node runs the new configuration.

The option file is read by the Erlang VM once, when the node starts, so a node restart is required for the new configuration to take effect. A hot upgrade does not replace the file; a package upgrade replaces it only when it was not modified locally. Set `EMQX_SSL_DIST_OPTFILE` to keep using a custom option file, including one that still disables verification. A node whose option file leaves peer verification disabled logs `erlang_distribution_tls_peer_verification_not_enforced` when it starts, in both security profiles.
