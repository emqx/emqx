The `mqtt` connector health check now verifies the connection end to end: it sends an MQTT `PINGREQ` and waits for the `PINGRESP`, bounded by `resource_opts.health_check_interval` / `health_check_timeout`, instead of only inspecting the local client state.  A remote broker that keeps the TCP connection open while packets are dropped is now reported as `connecting` within a couple of health check intervals instead of staying `connected` until the client's own keepalive expires (1 to 2 x `keepalive`, 160 s by default), so the action's buffer workers stop sending and keep the messages queued until the connection can be used again.

Connector status reasons no longer explain a connection closed by the peer as a listener capacity problem.
