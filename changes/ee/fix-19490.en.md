Fixed issues in the GreptimeDB connector with write syntax values: a number written to a tag was not stored as its string representation, including floats and tag templates that mix literals with placeholders; a quoted field value was rejected instead of being written as the string it contains; and an unquoted field template that mixes literals with placeholders was converted with charlist semantics, so for example `id_${n}` produced `id_A` instead of `id_65`. A tag value is now written as a string unless the rendered value ends in an `i`/`u` suffix or comes from a boolean in the message payload; the suffix is recognised on the rendered value, so text contributed by a placeholder cannot currently be told apart from a literal suffix. A tag that spells a boolean literal such as `T` or `F` therefore also gets a `STRING` column. An unquoted field value keeps its existing typing when it is a single typed value, while the number tokens of an unquoted field template that mixes literals with placeholders are rendered as text. A quoted field value is omitted for that point when any placeholder in it is unset; an unquoted field value is omitted only when it starts with an unset placeholder, and an unset placeholder elsewhere fails the write.

Note: GreptimeDB derives a tag column's type from the first write, and the type of a tag (primary key) column cannot be changed afterwards with `ALTER TABLE ... MODIFY COLUMN`. A table whose tag column was created as a number or a boolean therefore keeps rejecting the string form; write to a new measurement so that the column is created with the intended type. Existing rows are not rewritten.
