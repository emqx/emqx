## Summary

Support structured write points in the InfluxDB and GreptimeDB data
integrations, and templating of the InfluxDB bucket name.

### InfluxDB

The bucket (or database for InfluxDB v1/v3) is now an optional, template-based
parameter of the action. It overrides the bucket configured in the connector
per message, which allows dynamic bucket selection from the rule SQL result,
e.g. `bucket = "${payload.bucket_name}"`. If the rendered value is empty or the
referenced field is missing, the bucket configured in the connector is used.

The action now accepts a structured `write` array. Each point defines a
template-based measurement, tag entries, typed field entries, and an optional
timestamp with an explicit source precision. Multiple point definitions expand
each input message into multiple line protocol rows while preserving the
existing sync, async, batch, and dynamic bucket behavior. `write` and the
legacy `write_syntax` field are mutually exclusive.

Structured templates must contain one literal or one placeholder. Render
multiple values in the rule SQL result and use one placeholder in the action.
EMQX omits a structured tag or field when the placeholder in its key or value
is missing. A configured timestamp template that renders as missing is an
error. Use `timestamp = false` to let InfluxDB assign the current time.

InfluxDB v3 writes include the action timestamp precision in the write path.

A `write_syntax` line that consists of exactly one placeholder is now written
verbatim as a line protocol, which makes it possible to write a rule SQL select
result that is already a formatted line, e.g. `write_syntax = "${payload.line}"`.

### GreptimeDB

The GreptimeDB action and the EMQX Tables action backed by the native
GreptimeDB client now accept the same structured `write` array. This applies
to both the Erlang and native GreptimeDB drivers. Fields support `auto`,
`string`, `integer`, `float`, and `boolean`. Tags keep the existing
line-protocol typing rules. Multiple point definitions expand each input
message into multiple rows.

GreptimeDB tables require a time index. `timestamp = false` therefore uses the
current write time instead of rendering a point timestamp. Omitting the
timestamp configuration continues to use the message timestamp. GreptimeDB
`write_syntax` remains compatible, but raw-line pass-through is not included
in this change. The native GreptimeDB driver uses millisecond timestamps.

### Batch retries

The resource buffer retries a batch only when every failure in the batch is
recoverable. A successful write or a permanent failure makes the whole batch
non-retryable to prevent duplicate writes and repeated permanent failures.
Connection failures and timeouts remain retryable when the whole batch has no
successful or permanent result.
