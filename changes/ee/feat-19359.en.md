Added the `node.pinned_plugins` setting. It lists plugins that a node runs independently of the cluster plugin config, for example plugins that are built into a container image.

Set it to a comma-separated list of name-vsns, for example `EMQX_NODE__PINNED_PLUGINS="my_plugin-1.0.0"`, or to an array. A pinned plugin starts from the package in the node's own `plugins.install_dir` and is always enabled. It needs no `plugins.states` entry and no `plugins allow` grant. Its package and config are never copied from or to other nodes. Its config is the package default, merged with `etc/plugins/<name>.hocon` when that file exists. The node ignores `plugins.states` entries for the same plugin name, and cluster-wide plugin operations from other nodes skip it. When a pinned package is missing or fails to start, the node logs an error, raises an alarm, and keeps running.

`GET /api/v5/plugins` and `GET /api/v5/plugins/{name}` return a `pinned` flag for each plugin and for each node in `running_status`. On the node that pins a plugin, the stop and start actions of the API and CLI act on that node only, and a stop lasts until the node restarts. Other operations on a pinned plugin, such as install, uninstall, config update, boot order change and cluster sync, return HTTP 409 with the code `PLUGIN_PINNED`.

Nodes can now run different versions of the same plugin. The plugin must then stay compatible across these versions, for example in shared database tables, in RPC between its instances, and in its config.
