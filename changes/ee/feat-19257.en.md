Upgraded Erlang/OTP to 28.5.0.7-1.

With this version, TLS clients no longer accept a server certificate that has no subjectAltName (SAN) extension. Earlier versions fell back to matching the certificate's Common Name (CN) against the server name; that fallback is removed, following RFC 9525. This affects every TLS client connection that uses `verify = verify_peer`, including connectors, data integrations, authentication and authorization backends, and SSO. A connection to a server whose certificate has no SAN now fails with a `bad_certificate` alert.

The recommended fix is to reissue the server certificate with a subjectAltName entry for its host name.

As a transition aid, added the client TLS option `hostname_check`. The default, `san_only`, applies the new behavior. Set it to `san_or_common_name` to accept a certificate without SAN when its CN matches the server name. Certificates that have a SAN are always matched against the SAN only.
