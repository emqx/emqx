#+BEGIN_SRC erlang
perform(Act, NodeSpecs, Opts) ->
    ct:pal("~ping nodes: ~p", [Act, NodeSpecs]),
    Nodes = [Node || #{name := Node} <- NodeSpecs],
    try
        case do_perform(Act, NodeSpecs, Opts) of
            [] -> Nodes;
            Errors = [_ | _] ->
                ct:pal("cleaning up partially started nodes after ~p", [Errors]),
                catch stop(Nodes),
                error({Act, Errors})
        end
    catch
        K:R:S ->
            catch stop(Nodes),
            erlang:raise(K, R, S)
    end.
#+END_SRC

** TODO [#A] =emqx_ds_leaderboard= removes monitor entry with the wrong key
:PROPERTIES:
:FILE:  apps/emqx_durable_storage/src/emqx_ds_leaderboard.erl
:LINES: 225
:CUSTOM_ID: leaderboard-monitor-bug
:END:
#+BEGIN_SRC erlang
  M =
      case emqx_utils_maps:find_key(TableKey, M0) of
          {ok, MRef} ->
              demonitor(MRef),
              maps:remove(TableKey, M0);   %% BUG
          undefined ->
              M0
      end,
#+END_SRC
Facts:
- =monitors= is =#{reference() => table_key()}=.
- =emqx_utils_maps:find_key/2= returns the *key* (=MRef=), so
  =maps:remove(TableKey, M0)= is a no-op (tuple vs reference key).

Consequences:
1. Monitors map leaks one entry per graceful unregister — unbounded growth
   over shard/leader churn.
2. =demonitor/1= (no flush) can leave a stale ='DOWN'= already in the
   mailbox; because the =MRef= entry is never removed, that stale ='DOWN'=
   matches, and =mria:dirty_delete(?tab, TableKey)= deletes a *freshly
   re-registered* row (same =TableKey=) — silently dropping a live
   leader/replica from =whereis_leader/2=, which now feeds
   =emqx_ds_builtin_raft:leader_node/2=.

*Fix:*
#+BEGIN_SRC erlang
  {ok, MRef} ->
      demonitor(MRef, [flush]),
      maps:remove(MRef, M0);
#+END_SRC
Also: the =terminate(_Reason, undefined)= clause is dead code (state is
never =undefined= in this module).

** TODO [#A] Node can report ready after a failed business-app startup
:PROPERTIES:
:FILE:  apps/emqx_machine/src/emqx_machine.erl
:CUSTOM_ID: ready-after-failure
:END:
Chain of facts:
1. classy's hook runner swallows exceptions: =classy_hook:safe_apply= logs
   =?classy_hook_failure= (critical) and returns =error=;
   =classy_boot= uses =foreach= and *continues* the run-level climb.
2. If =manage_business_apps(enter, ?emqx_rl_boot)= -> =post_boot()= ->
   =ensure_apps_started()= fails midway, the level still reaches 300.
3. =on_run_level(enter, ?emqx_rl_ready)= then sets =?cluster_ready=, so
   =is_cluster_ready/0=, =is_ready/0= (=classy_boot:run_level(ready) >= 300=)
   and =can_i_join= all answer "ready" with business apps half-started.

The old boot path failed loudly, and =is_ready= was tied to
=emqx_machine_terminator=.  (=register_business_hooks= already uses
=timeout => infinity=, so the 30 s-interruption variant is handled — the
*exception* variant is not.)

*Fix:* on ={enter, ?emqx_rl_boot}= failure, either block the run level or
take the node down; do not let =?cluster_ready= be set afterwards.
